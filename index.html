TL;DR

  1. Rubin 提供了什么？22 TB/s 的 HBM4，以及能在矩阵乘法内部把 3-bit index 解压成 8 个 E4M3 数值的 LUT-B Tensor Core。
  2. 它能解决什么？静态 3-bit weight 是最自然的 B operand，但动态 Kᵀ 与 V 同样合法。Q 和 softmax 后的 P 以 MXFP8 留在 A，因此 Rubin 可以同时针对 model-weight bandwidth 与被反复读取的 KV-cache bottleneck。
  3. 为什么不能直接用朴素 INT3？Outlier 会毁掉它：Qwen3-4B 的 8K PPL 从 9.468 暴涨到 1504。离线 Lloyd–Max[1][2] codebook —— 加上 OSCAR[3] rotation 和 BF16 sink/recent 窗口 —— 能拉回到约 10.4。
  4. 为什么选择 10M？在 Kimi K3 MLA TP8 thought experiment 中，1.56-TB weights 完美切分后，每张 288-GB Rubin 剩 93 GB。10M-token K3V3 latent 加 native RoPE 使用 78.7 GB， 每 GPU 还剩 14.3 GB 给 runtime。零预留数学极限是 11.81M；当前 checkpoint 本身仍然只支持 1M context。
术语说明。Lloyd–Max 是经典的 non-uniform scalar quantization 算法： 在固定刻度数量下，交替执行 nearest-center assignment 与 centroid update，以最小化均方重建误差 [1][2]。 OSCAR（Offline Spectral Covariance-Aware Rotation）则在低比特 KV-cache quantization 之前，离线学习固定的、attention-aware 的逐层 rotation 与 clipping threshold [3]。

1Intro：Vera Rubin 最近到底变了什么？

1.1 从“faster GPU”变成 agentic inference platform

NVIDIA 对 Rubin 的官方叙事是 agentic AI：更长 context、更多 reasoning steps、更高 decode interactivity， 以及 rack-scale orchestration。单张 Rubin GPU 的公开规格包括 224 SM、896 Tensor Cores、288 GB HBM4 和 22 TB/s HBM bandwidth；Vera Rubin NVL72 则把 72 张 GPU 连接成一个 NVLink 6 scale-up domain。

1.2 为什么我们特别关心 KV cache？

Community 常用一句话概括 inference：prefill is compute-bound, decode is bandwidth-bound。 Medium 的 disaggregated inference 文章用这个框架解释了为什么 HBM、KV movement 和 prefill/decode separation 会变得越来越重要。

对长 context decode，每生成一个 token，都需要重新读取历史 K/V。模型越小、context 越长、batch 越高， KV traffic 越可能从配角变成主要瓶颈。因此 Rubin 的 22 TB/s HBM4 很重要；但更有意思的是，它还带来了 减少 bytes/value 的新 ISA。

1.3 用 CUDA 13.4 探测 Rubin ISA

SemiAnalysis / InferenceX 报道了第一版公开 SM107 software stack：CUDA 13.4、PyTorch、vLLM 和 OpenAI Triton 开始加入 Rubin 支持， 同时披露了 3-bit programmable LUT Tensor Core。

我们实际安装了 CUDA 13.4.46 Developer Preview，并使用：

  • PTX ISA 9.4
  • sm_107a
  • ptxas
  • cuobjdump
  • nvdisasm

这让我们至少可以做 compile-time legality check。需要注意，vLLM 的 SM107 tracking issue 仍然是 open，Triton 也只是 initial Rubin support； software bring-up 还没有结束。

2最相关的新特性：3-bit programmable LUT-B

2.1 LUT-B 在做什么？

普通 FP8 B matrix 每个值需要 8 bit。Rubin LUT-B 改为：

  1. 每个位置只存一个 3-bit index；
  2. index 从 8-entry E4M3 LUT 中选择 reconstruction value；
  3. Tensor Core 在 tcgen05.mma 内部完成 lookup；
  4. kernel 不需要先 materialize 一个 decompressed B matrix。

SemiAnalysis 描述的 granule 是 K=64 × N=8 = 512 values：

512 × 3-bit index = 192 bytes
8 × E4M3 LUT      =   8 bytes
--------------------------------
total             = 200 bytes
effective         = 3.125 bit/value

LUT 不要求 uniform spacing，因此可以放 Lloyd–Max[1][2] 这种 non-uniform centroids。这也是 3-bit 仍可能保住质量的关键。

2.3 3-bit weight 是最自然的 LUT-B 用法，KV 使用同一个 primitive

目标MXFP8 A3-bit LUT-B解决的 bottleneck仍然困难的部分
Weight W3A8activation X离线 pack 的 Wᵀ模型 weight 容量与 decode weight bandwidth量化精度与 small-batch M occupancy
KV K3V3先 Q、后 P动态 Kᵀ、后 V长上下文 KV 容量与反复读取的 HBM trafficruntime packing、paged layout、operand 方向与 row packing

Weight 映射更简单：Y = X × Wᵀ 天然把静态、可离线 transpose 的 weight matrix 放在 B； 每个 64 × 8 granule 可以提前 pack 成 512 个 indices 加一张 8-value E4M3 LUT。这是 3-bit storage + E4M3 reconstruction，不是普通 INT3 arithmetic。

这条 instruction 并不要求 B 必须是 static weight。动态 Kᵀ 与 V 同样可以成为 B operand，因此 Rubin 也能把相同的 in-MMA lookup 用到 KV-cache bottleneck：长上下文 decode 会反复读取 历史 KV，减少这些 bytes 可以同时缓解容量和 HBM traffic。KV 更难实现，但并不是次要用途。

3我们做了什么：把 LUT-B 映射到 attention

Rubin LUT-B 有一条最重要的规则：它只在 MMA 内解压 matrix B。因此我们不把整个 attention 都压成 3-bit，而是压缩每个 decode step 都会反复读取的 cache；Q 和 P 仍作为 MXFP8 matrix A。

3.1 GQA KV 与 MLA latent：同一条配方，两种 cache

两种架构走的是同一条四步路径：

  1. Cache 只写一次。离线准备 codebook；token 进入低精度区域时，只保存 3-bit index 和 8 个 E4M3 lookup values。
  2. 第一次 LUT-B MMA。MXFP8 Q 作为 A，压缩 cache 作为 B，计算 attention scores。
  3. Softmax 保持 FP32。max、exp、sum 和 normalization 不降到 INT3；得到的 P 留在片上， 再转成 MXFP8。
  4. 第二次 LUT-B MMA。MXFP8 P 作为 A，同一类压缩 cache 作为 B，得到 attention output。

差别只在“压缩哪一份 cache”：

  • GQA / MHA（Qwen、Gemma）缓存独立的 Kᵀ 和 V，所以每层有 K/V 两套 codebook，也可以有独立的 R_k / R_v。sink 64、recent 256 和未满 block 保持 BF16。
  • MLA（Kimi K3）不展开 K/V，只缓存一份共享的 512-d latent c_KV，所以每层 只需一套 codebook 和一个 latent rotation。Kimi 的 69 个 KDA states 与 64-d RoPE suffix 保持原生精度； 只有 24 个 Gated-MLA layers 的 latent 进入 K3V3。

上面提到的 BF16 sink/recent 窗口值得单独介绍，因为本文所有方案都保留它。cache 中各位置的 敏感度并不相同：最前面的 64 个 token 是 attention sink —— 会吸收不成比例注意力权重的位置； 最近的 256 个 token 则是 decode 引用最频繁的部分。这两段始终保持 BF16、不进入 3-bit 路径； 一个 token 只在离开 recent 窗口、且所在 512-value block 填满时，才被一次性打包进 LUT-B granule。 §4.2 的消融分别量化了两者的贡献；窗口与 rotation/clipping 配方沿用 OSCAR 论文。

这里最重要的是：INT3 cache 不需要先解压回 HBM。Tensor Core 在 UTCQMMA.LUTB 内一边 lookup、 一边做乘法。Q/P 使用 E4M3 element + UE8M0 block32 scale；Qwen3-4B 的 GQA 还可以通过 B_KEEP → B_REUSE，让一个 K/V tile 服务 4 个 Q heads。

3.3 Lloyd–Max：把 8 个刻度放到真正需要的位置[1][2]

3-bit 只能表示 8 个值。最简单的 uniform quantization 会把 8 个刻度等距排开；如果大多数值挤在 0 附近、 只有少量 outlier 很大，很多刻度会浪费在几乎没有数据的区域，0 附近反而分得太粗。

Lloyd-Max 的做法很直接：

  1. 在 calibration data 上先放 8 个初始中心。
  2. 每个数分给离它最近的中心。
  3. 把每组中心移动到这一组数据的平均值。
  4. 重复第 2、3 步直到基本不再变化，最后只做一次 E4M3 rounding。

这个过程完全离线进行。Serving 时不再迭代，只需找到最近的一个中心并保存其 3-bit index。GQA 每层分别拟合 K/V 两套 8-value codebook；MLA 每层只拟合 latent 的一套 codebook。

3.4 OSCAR：先把尖峰摊平，再交给 3-bit[3]

Lloyd-Max 解决的是“8 个刻度放在哪里”，但如果少数维度特别大，3-bit 仍然很难表示。 OSCAR 可以理解为： 先旋转坐标系，把集中在少数维度的尖峰摊到更多维度，再量化。

具体只有三步：

  1. 在 calibration data 上为每层学习一个 orthogonal rotation。
  2. 写 cache 前先 rotation，并裁掉极少数最极端的 outliers，然后用 Lloyd-Max K3V3。
  3. 在 QK/PV 的另一侧做对应变换或 inverse rotation，让原来的 attention 数学关系保持不变。

GQA 可以分别使用 R_k 和 R_v；MLA 因为 K/V 共享同一个 c_KV，只能使用 一个 latent rotation，并把对应变换吸收到 absorbed-query 和 value projection。最简单的记法是： Lloyd-Max 调整尺子的 8 个刻度，OSCAR 先把要量的东西铺平。

5通用性能模型：GQA、MQA 与 MLA

通用 roofline 很简单。令 P_LUTB 为尚未公开的 Rubin LUT-B full-tile throughput， B_HBM 为实际 HBM bandwidth，R_local 为单张 GPU 上能够复用同一 compressed B tile 的 query rows 数量；对于 T 个 query tokens： 

useful M occupancy = min(R_local × T / 128, 1)
attention throughput = min(B_HBM × arithmetic intensity,
                           P_LUTB × useful M occupancy)

架构同时决定 R_local 与 arithmetic intensity。下表假设同一 cache tile 能在列出的 local heads 间复用；tensor/context parallelism 可能减少这个数量。

架构Cache 被谁共享T=1 时有效 A rows理想 cache AISmall-M 含义
MHA单个 query head116 / b最容易受影响
GQAg = Hq / Hkv 个 query headsg16g / bGQA4 只填 4 / 128 rows
MQA全部 local query headsH_local16H_local / b通常填得更满

因此不能把 GQA4 的警告直接套到 MLA。 Kimi K3 的 unsharded MLA layer 中，96 个 query heads 共享同一个 512-d latent，名义 row occupancy 是 96 / 128 = 75%，不是 4 / 128 = 3.125%。 MLA 避开了严重的 GQA4 underfill；但 latent 的复用率很高，仍可能变成 compute-bound。部署切分与 hybrid model 中非 MLA 部分的影响单独放在 §7。

普通 tensor parallelism 不会把 context limit 再乘 8：共享 MLA latent 通常会复制到各 TP ranks。 单独设计 sequence/context-parallel KV sharding，aggregate 数学上限可以接近 94.5M，但会引入另一套通信与 kernel 问题。Loaded weight memory、allocator fragmentation、workspace、activation，以及模型原生的 1M positional limit 都使 11.81M 只能作为 upper bound，而不是可直接部署的配置。

H100/B200 两行只是“如果 HBM 只搬这些 compressed bytes”的 normalization ceiling，不是可执行的 native K3V3 performance。它们必须先用 software unpack/dequantize，实际会增加 instructions、temporary traffic 和 latency。Rubin 的区别是 lookup 发生在 Tensor Core MMA 内。Rubin 这一行同样只是 byte-only HBM ceiling，不是硬件预测。

在 byte 数字之上，第一个需要补充的 roofline 细节是 operand 方向。把 decode 写成 K × Qᵀ / Vᵀ × Pᵀ 时，长 KV 位于 A 的 M 方向，短 Q/P 位于 B 的 N 方向；对非常 skinny 的 GEMV， 这个方向更容易填满不对称的 MMA tile。但是 LUT 解压只支持 B，所以 compressed KV 必须使用 Q × Kᵀ / P × V 的方向。

我们在审计最新的 decode path 时发现： FlashInfer SM100 CuTe GQA decode kernel 明确设置 mma_tile_m=128；GEMM1 的 A 是 K、B 是 Q，GEMM2 的 A 是 V、B 是 P。它让 sequence/head-dim 填满 A 的 M 方向，并把 GQA heads × prediction tokens 填进 B 的 N 方向。需要同时区分 其他实现：FlashInfer 旧的 prefill/Tensor Core path 与 FlashAttention-3 也存在 Q/P-as-A、KV-as-B 的排布。因此 operand 角色不是 GQA 的数学规定，而是 kernel-specific schedule；最新的 CuTe decode kernel 确实选择了 KV-as-A —— 而这恰好是 LUT-B 对 compressed KV 禁止的方向。对 LUT-B 来说 Q/P 必须放 A， 于是问题变成 single-token decode 时 A 的 M tile 有多空。

PTX 的 kind::mxf8f6f4 shape 是 M=128、N 从 8 起。Qwen3-4B 的 GQA ratio 是 4，所以一个共享 K/V tile 最多把 4 个 Q heads 打包成 4 行：

7Limitations：哪些问题必须等 Rubin 硬件？

  1. LUT-B throughput 尚未公开。CUDA 13.4 只能证明 instruction 可以编译，不能给出 full-tile latency 或 throughput；8.75 与 17.5 PFLOP/s 都只是 sensitivity cases。
  2. 有效 rows 取决于 local schedule。GQA 使用共享同一 local KV tile 的 query heads； MLA 可以使用共享同一 latent 的全部 local heads。Kimi K3 有 96 个 global heads，未切分时名义上能填 M=128 的 75%，不会遇到严重的 GQA4 bottleneck；但 tensor/context parallelism 会减少单张 GPU 可打包的 heads，因此实际 MLA occupancy 仍取决于部署。
  3. HBM 与 collector efficiency 未知。Achieved bandwidth、LUT/codebook traffic、 B_KEEP → B_REUSE、descriptor、swizzle 与 TMEM movement 必须一起实测。
  4. Rubin fused kernel 尚未实现。Softmax、同步、page-table traversal、launch overhead 与 scheduling 都可能把瓶颈移出孤立的 QK/PV roofline。
  5. QAT 是很有价值的 future exploration。Quantization-aware training 可以让模型直接适应 精确的 3-bit indices、E4M3 LUT centroids、可选 UE8M0 B scales、clipping 与 absorbed projections， 而不是在冻结 checkpoint 后再补偿量化误差。本文目前没有 QAT result。
  6. Hybrid model 会稀释 layer-local gain。Kimi K3 只有 24 个 Gated-MLA layers， 另有 69 个 KDA layers，其 states 在本实验中保持原生精度；MLA attention estimate 不是整模型加速。
  7. 10M 是 HBM capacity target，不是已支持或实测的 context。当前 Kimi K3 checkpoint 的 positional limit 是 1M；PPL/KL 只测到 8K，GPQA 也不能验证 million-token retrieval 或 generation quality。
没有硬件就无法知道具体加速。至少需要在 fused Rubin attention kernel 上实测 decompress::lut::b full-tile throughput、各架构的 local row packing、achieved HBM bandwidth 与 collector reuse。上面的所有数字都只是解析上限，不是 Rubin silicon data。

8这个故事目前说明了什么？

  1. 普通的 3-bit KV 无法承担 serving。Naive uniform INT3 直接崩溃 —— 8K PPL 从 9.468 涨到 1504、KL₅₀ 涨到 5.15，任何 sink/recent 窗口都救不回来。
  2. OSCAR + Lloyd-Max 能把质量带回来。离线 per-layer codebook 加 rotation/clipping 把 Qwen3-4B 拉回 PPL ≈ 10.4、KL₅₀ 最低，并把 Kimi K3 的 GPQA 从 83.16% 提到 89.73% —— 全部在 ISA 规定的 Q/P 契约（E4M3 + UE8M0 block32）下完成。
  3. 一个 LUT-B primitive 可以解决两类 bandwidth 问题。W3A8 是最自然的 static-weight mapping；动态 K3V3 更难实现，但可以直接减少长上下文 decode 的 KV 容量与反复读取流量。
  4. Decode-shape 问题与架构有关。GQA4 暴露出严重的 4 / 128 small-M case；MLA 的一个 latent 被全部 local query heads 共享，因此不受 GQA ratio bottleneck 约束，但 sharding 仍决定它的 local occupancy。
  5. 10M headline 保留了有限但非零的 HBM headroom。完美 weight sharding 下零 workspace ceiling 为 11.81M；选择 10M 会使用每 GPU 93 GB 剩余空间中的 78.7 GB，留下 14.3 GB，还没有计入模型 原生的 1M positional limit。
  6. Performance 不只看 bytes，而且公开信息还不够。1M 下 Qwen GQA4 scenarios 相对 H100 BF16 为 20.4×–33.6×；只有 Rubin 硬件才能给出真实 tile throughput 与具体加速。

Reproducibility

全部从公开的 OSCAR branch 运行，所有路径相对于 repository root：

git clone https://github.com/FutureMLS-Lab/OSCAR.git && cd OSCAR
git checkout zhongzhu/oscar-int3-rubin-simulate
  • Speed tables（§6）：python3 rubin/rubin_k3v3_roofline.py --compare-hardware —— 只依赖 Python 标准库。
  • ISA compile proof：rubin/run_compile_probes.py --cuda /usr/local/cuda-13.4 —— 需要 CUDA 13.4 preview toolchain；校验生成的 SASS 包含 UTCQMMA.LUTB。
  • Operand-orientation microbench： rubin/benchmark_decode_operand_orientation.py —— 需要支持 FP8 的 PyTorch GPU； block-scaled case 另需 sgl_kernel。
  • Kimi K3 latent K3V3 quality：runtime patch、codebook fitter、PPL/KL/GPQA clients 与汇总脚本全部位于 rubin/。按照 rubin/README.md 操作，并将 rubin/run_quality_client.sh 指向兼容的 SGLang endpoints。

H100/B200 仅作 numerical oracle —— physical cache 仍会 reconstruct 成 BF16，这里没有任何 Rubin 实机 latency。大模型 checkpoint、数据集与运行结果不入 branch。
